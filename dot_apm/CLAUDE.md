# dot_apm/ — APM manifest

このファイルは Claude Code が `dot_apm/` 配下で作業するときだけ読み込まれる repo-only の文脈ファイル(`.chezmoiignore` の `.apm/CLAUDE.md` で除外。同じディレクトリの `apm.yml` は `~/.apm/apm.yml` に配置される)。ルート `CLAUDE.md` には、Key Patterns の 1 行のポインタと、`~/.claude.json` symlink のルール(トポロジを仮定しない / `scripts/apm-install-global.sh` を使う / `mv` 前のガード)だけがある。一次証拠と実測の詳細は下の「`~/.claude.json` symlink と APM」節にある。

## `dot_apm/apm.yml` + APM (microsoft/apm)

**`dot_apm/apm.yml` + APM (microsoft/apm)** — Declarative manifest for MCP servers only (`dependencies.mcp`), deployed to `~/.apm/apm.yml`. Skills / plugins は APM ではなく Claude Code ネイティブの marketplace で管理し(ルート `CLAUDE.md` Key Patterns の「Skill/plugin management via native Claude Code marketplace」)、`apm.yml` に `dependencies.apm` は無い。 `.chezmoiscripts/run_onchange_after_apm-install.sh.tmpl` runs the installer only when `apm.yml`'s (or the installer's) hash changes (a plain hash-gated `run_onchange_`, not `run_after_`), and writes MCP servers into the top-level `mcpServers` key of `~/.claude.json` **and** into the `[mcp_servers.*]` tables of `~/.codex/config.toml`. The `.tmpl` only dispatches; the logic lives in `scripts/apm-install-global.sh`, a plain `.sh` so shellcheck/shfmt/bats can see it (`just test-apm-install`). That script wraps `apm install --global --target claude,codex` in a guarded de-link/re-link of the `~/.claude.json` symlink, because APM 0.30.0 refuses to prune through a symlink while still flattening one on add — the mechanism, the reason the link cannot simply be abolished (nono re-creates it on every sandboxed launch, `/bin/true` included), and the guard that must never be dropped are in the「`~/.claude.json` symlink と APM」section below (the root `CLAUDE.md` Known Pitfalls keeps only the rules). Use that script rather than calling `apm install --global` directly. A target declaration is required — `apm install --help` resolves targets in the order `--target` > `apm.yml`'s `targets:` > `apm config set target` > auto-detect, and with *neither* declaration present it falls back to auto-detect and fans out to every "global-capable" runtime it finds (Gemini CLI, Kiro, etc.). The target list is declared **twice on purpose**, in `apm.yml`'s `targets:` and in the script's `--target`, so that a typo or a key rename in one of them cannot silently fall back to that fan-out. Because the flag wins over the manifest, the two must be kept in step — a target added to `apm.yml` alone has no effect in production; `test/apm-mcp-distribution.bats` compares the two lists statically so CI catches the divergence without the apm CLI. Codex is a target but Cursor is not, and `apm.yml` deliberately declares no `codex` MCP server (APM has no per-server target selection, so distribution is all-or-nothing and declaring it would ship Codex to itself); the reasoning and APM's exact ownership semantics are in `docs/adr/0006-apm-owns-only-the-mcp-servers-table-of-codex-config.md`, with the behaviour pinned by `test/apm-mcp-distribution.bats`. APM owns only the `[mcp_servers.*]` tables of `~/.codex/config.toml` — `[projects.*]` trust records and everything else there stay Runtime State. Hash-gating is sufficient here because `~/.claude.json` has no competing chezmoi-owned `.tmpl` that re-renders it every apply — see [run-after-vs-run-onchange-for-shared-config-ownership.md](../docs/solutions/architecture-patterns/run-after-vs-run-onchange-for-shared-config-ownership.md) for the general criterion. chezmoi は `~/.claude.json` の実体(nono 0.79.0 では `~/.claude/.claude.json`)を直接管理しない(`.chezmoiignore` 済み)。 Some plugins bring their own MCP servers independent of `dependencies.mcp` (e.g. `getsentry/plugin-claude`'s native-marketplace `sentry` plugin), so `dependencies.mcp` is only a subset of the MCP servers actually deployed — check the live `mcpServers` key, not just `apm.yml`, to see the full set. Running `apm install <pkg>` by hand appends the dependency straight to `~/.apm/apm.yml` (the deploy target, fully owned by chezmoi via `dot_apm/apm.yml`) and that edit is silently lost on the next `chezmoi apply` — always declare new dependencies in `dot_apm/apm.yml` instead. `docs/superpowers/specs/2026-08-02-apm-skill-mcp-management-design.md` は MCP+Skill 統合の設計文書だが、現行と一致するのは MCP の節だけで Skill の節は現在の構成を表していない。

## `~/.claude.json` symlink と APM

**`~/.claude.json` topology has changed before and may change again — never assume, always check with `ls -la`/`file` before writing.** Writing back through a symlink target replaces it with a plain file (verified: `chezmoi apply -S <tmp> -D <tmp>` turned a `120755` symlink into a `100644` regular file) — so a future `modify_` script that assumes today's topology can silently break it. Nothing in this repo manages either file directly (APM's `apm install --global` writes to whichever `~/.claude.json` resolves to at runtime). `.chezmoiignore` excludes **both** paths regardless of topology (the symlink entry alone would let a bulk `chezmoi add ~/.claude` pick up the 0600 real file). **その symlink を作っているのは nono**。`nono run --profile claude-seal` は**コマンドが `/bin/true` でも**実行のたびに実体を `~/.claude/` へ移して link を張り直す(実測)。サンドボックスが `$HOME` 直下を許可せず `~/.claude` を丸ごと許可しているための再配置(nono 内の対比ペア: `: > ~/.claude/.deadbeefcafe1234.tmp` → OK / `: > ~/.deadbeefcafe1234.tmp` → `Operation not permitted`)。実体の名前は nono のバージョンで変わる: 0.72.0 は `~/.claude/claude.json`、0.79.0 は子プロセスに `CLAUDE_CONFIG_DIR=$HOME/.claude` を渡し、実体は `~/.claude/.claude.json`(バイナリの文字列は `Cannot create Claude compatibility symlink:`)。0.79.0 ではこれでグローバル設定の書き込みが nono 内でも永続する(2026-10-09 に実測。詳細は `dot_config/nono/CLAUDE.md`)。**link を手で消しても意味が無い**(次の nono 起動で戻る)。


**APM の壊し方は 2 通りあり、向きが逆**。追加(configure)側は今も `atomic_write_text` = `os.replace()` なので symlink を平のファイルに潰し、旧実体(`readlink` で指していたファイル)を取り残す(split-brain)。prune 側は 0.30.0 で `_reject_symlink_config` が入り、潰す代わりに `[x] Refusing to clean symlinked MCP config` で install 全体を失敗させる。prune が走るのは `apm.yml` から MCP 依存を消したときだけなので、普段は成功し依存を消した日だけ落ちる。**`apm install --global` は素で叩かず `bash scripts/apm-install-global.sh` を使う** — de-link → install → re-link をガード付きで回す(`.chezmoiscripts/run_onchange_after_apm-install.sh.tmpl` もこれを呼ぶ)。

**手で de-link したときは、戻す `mv` の前に link の実体(de-link 前の `readlink ~/.claude.json`。nono 0.79.0 では `~/.claude/.claude.json`、以下の事故当時の 0.72.0 では `~/.claude/claude.json`)が存在しないことを必ず確認する。** 2026-09-24 にこれを怠って設定を失った: de-link 中に nono の実行が挟まると link が復活して実体が `~/.claude/claude.json` へ戻るため、`mv ~/.claude.json ~/.claude/claude.json` が **symlink で実体を上書きし**、両方が同じ相対パスを指す宙吊りの link だけが残る(`~/.claude/.claude/` はその形の残骸)。`mv` は symlink の mtime を保存するので、事後に「いつ張り直されたか」は残った link の mtime から読める。 nono 0.79.0 では、link の復活とは別にもう 1 つの経路がある: 実行中の nono セッションは `CLAUDE_CONFIG_DIR` 経由で実体のパスへ直接書くので、de-link 中に設定を書くだけで実体が再出現する。回帰テストは `test/apm-install-global.bats`。
