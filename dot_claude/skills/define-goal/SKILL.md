# define-goal

`/goal` に渡す Goal Condition(用語は chezmoi リポジトリの `GLOSSARY.md`)を、ユーザーと往復しながら組み立てる。成果物は貼り付け用の `/goal <Goal Condition>` 1 行だけ。`/goal` を打つのも作業を始めるのもユーザーで、このスキルは作業に手を付けない。

## Goal Judge が読めるもの

Goal Condition の書き方の規則は、すべて Goal Judge の性質から来ている(正本: https://code.claude.com/docs/en/goal )。

- 毎ターンの終わりに小さく速いモデルが会話の記録だけを読み、Met / Not yet met / Impossible を返す。ツールを呼ばないので、ファイルの中身もコマンドの結果も、Claude が会話に出したものしか見えない。
- 会話に残った古い出力も証拠として読む。途中のターンで通ったテストの出力が残っていれば、その後の変更で壊れていても Met と判定しうる。
- Impossible はゴールを解除して制御をユーザーに返す。Not yet met なら、Claude が質問を出してターンを終えても答えを待たずに次のターンが始まる。ツールを呼ばないターンが数回続いたときだけループが止まり、ゴールを残したまま制御がユーザーに戻る。判定はユーザーの次の返信の後に再開する。
- Goal Condition は 4,000 字まで。

## 1. 意図を読む

引数の種類ごとに材料を集める。

- **自由文**: そのまま意図として扱う。
- **Requirements Document のパス**: 読んで、AC(Acceptance Criteria)を列挙する。
- **issue 番号または URL**: `gh issue view <番号または URL> --json title,body` で本文を読み、AC があれば列挙する。
- **引数なし**: 何を終わらせたいかを 1 問だけ聞く。

検証に使うコマンドは、リポジトリの `justfile` / `package.json` / `Makefile` / `CLAUDE.md` などから実在の名前を調べる。事実はユーザーに聞かない。

完了条件: 到達状態の候補と、それを示すコマンドの実在の名前が揃っている。コマンドで示せない意図なら、そのことが分かっている。

## 2. 案を作る

Goal Condition は次の 5 要素をこの順に、「。」で区切った 1 段落の日本語で書く。コマンド名・パス・数値はバッククォートで囲む。

1. **到達状態**: 測れる終状態を 1 つ。テストの結果、終了コード、件数、空のキューなど。「進める」「改善する」のような活動は、終わったときに何が真になっているかに書き換える。
2. **検証**: 「最後の変更の後に `<コマンド>` を実行し、<合格の判定> をその出力で示す」。この句は必ず入れる。合格の判定は「exit 0」「失敗 0 件」のように出力から読める形にする。
3. **制約**: 到達までに変えてはいけないもの(触らないファイル、公開 API、既存のテストなど)。意図・Requirements Document・issue から読めるものだけを書く。
4. **達成不可能とみなす事態**: 「次のどれかが起きたら、このゴールは達成不可能とみなす: …」。人の判断が要る場面を書く。例: 公開 API の変更が必要になった、制約を破らないと到達できないと分かった。
5. **打ち切り句**: 「`20` ターン経っても到達していなければ、未達の項目を報告したうえで、このゴールは達成不可能とみなす」。上限に達したゴールを Met ではなく Impossible で終わらせ、達成として記録されないようにする。ユーザーが数を指定したらその値にする。

### Requirements Document か issue から作るとき

AC の本文は Goal Condition に写さない。検証の要素を次の形にする: 「最後の変更の後、最終ターンで `<パスまたは issue>` の AC ごとに、満たしたことを示す証拠(実行したコマンドと出力の該当行)を並べた checklist を出す。証拠の無い AC が 1 つでも残れば未達」。Goal Judge はファイルも issue も読めないので、AC の判定材料は Claude が会話に出す checklist だけになる。

### コマンドで示せない意図のとき

「UI が見やすくなる」のように出力で証明できない意図には、ユーザーの返信を検証に使う案を出す: 「`<確認対象>`(スクリーンショットのパスなど)を示した後はツールを呼ばずに返信を待ち、ユーザーが OK と返信する」。待つ間にツールを呼ぶとループが止まらず、打ち切り句のターンを使い続ける。ユーザーの返信も会話の記録に残るので、Goal Judge が判定できる。この案が断られたら、`/goal` には向かない意図だと伝えて終える。

### 長さ

案が 2,000 字を超えて見えるときは、ヒアドキュメントで文字数を数える(`LC_ALL` を UTF-8 にしないと `wc -m` はバイト数を返し、日本語を約 3 倍に数える)。

```bash
LC_ALL=en_US.UTF-8 wc -m <<'EOF'
<案>
EOF
```

4,000 字を超えていたら制約と達成不可能の事態から、意図に照らして重要度の低いものを削る。

完了条件: 5 要素がすべて埋まり、4,000 字以内に収まっている。

## 3. 往復する

ラウンドごとに、その時点の案をコードブロックで示し、続けてユーザーの判断が要る点だけを番号付きで、推奨案を添えて問う。問うのは判断(どこまでを到達状態にするか、何を制約にするか、何ターンで打ち切るかなど)で、手順 1 で調べられる事実は問わない。回答を反映した案で次のラウンドに進み、回数に上限は設けない。

完了条件: ユーザーが案を変更なしで承認した。

## 4. 出す

承認された案を、次の 2 つだけで出す。

- `/goal <Goal Condition>` を 1 行で書いたコードブロック 1 つ
- 「無人で回すなら auto mode で打つ(Manual mode では許可済みでないツール呼び出しのたびに確認が入る)」の 1 行
