# scenario-authoring — 観点導出とシナリオ実装

## 観点の導出

入力: `git diff <base>...HEAD`(base はデフォルトブランチ。`git symbolic-ref --short refs/remotes/origin/HEAD`
で求め、失敗したら推測せずユーザーに聞く。PR があれば description も)。

**ブラックボックス志向で列挙する。** 「diff で書き換わった行」起点ではなく
「観測できる振る舞いの契約がどの画面・導線に現れるか」起点で考える。
コード検索(コンポーネントの利用箇所・ルーティング)は、現れる場所を漏れなく
特定するための網羅補助として使う。

各観点は次の 3 点セットで書く:

- **前提**: どんなデータ・状態が必要か(`seed/features/<feature>.ts` か `seed/common.ts` が用意するもの)
- **操作**: 画面で何をするか
- **期待結果**: 機械判定可能な述語(URL 遷移・表示内容・件数差分など)

**期待結果が diff・PR description から導けない場合は捏造せず、不明点を列挙して
ユーザーに質問する。** もっともらしい期待値をでっち上げた観点は、pass しても
fail しても誤った情報になる。

観点に含めるもの: 変更した機能の主要導線 / 境界値・エラーケースのうち画面で
観測できるもの / 変更が波及しうる既存画面(デグレ確認)。
含めないもの: 単体テストで担保済みの内部ロジック / 画面から観測できない副作用。

## 承認ゲート(機能の初回のみ)

その機能の初回(`scenarios/<feature>/` が無い)では、観点リスト(3 点セット)を本文に番号付きで提示し、
`AskUserQuestion`(選択肢は「承認」「修正したい」。修正・削除の内容は自由入力で受ける)で
承認を受けてから実装に入る。スイート自体が既にあっても、
別の機能を初めて足すときは初回として扱う。
既に `scenarios/<feature>/` がある場合は、diff から差分観点のみを導出して
承認なしで追加し、実行後の報告で「今回追加した観点」を明示する。
質問できない状況(review-verify のサブエージェントなど)では承認ゲートを飛ばし、
報告に「未承認の観点」として一覧を出す。

## spec の記述規約

お手本: `<skill-dir>/assets/example.spec.ts`(コピーせず読んで倣う。`<skill-dir>` は SKILL.md の冒頭で定義)。

- 1 観点 = 1 `test()`。test 名は日本語で、承認済み観点リストの文言をそのまま使う
- 判定は durable な状態への `expect` で行う。トースト・フラッシュメッセージ等の
  一時表示は「出て消えた」と「出なかった」を区別できないため本判定に使わない
  (補助的に映像へ残るのは良い)
- セレクタは `getByRole` / `getByLabel` を優先。テキスト照合は完全一致を避け
  部分一致にする(テンプレート由来の空白・改行が DOM に残ることがある)
- 固定 sleep(`waitForTimeout`)を使わない。Playwright の auto-waiting と
  `expect` のリトライに任せる
- 件数差分を判定に使う場合、`locator.count()` は auto-wait しないため、seed 済みの
  既知行の表示を `expect(...).toBeVisible()` で待ってから件数を取得する
  (一覧が非同期描画されるアプリで描画前の過小な件数を拾わないため)
- シナリオ間・機能間の実行順依存を作らない。観点固有の前提データは `seed/features/<feature>.ts` で
  固定の識別子を付けて用意し、他シナリオ・他機能が作ったデータに依存しない
- 新しい観点を追加したら README.md の観点一覧表にも 1 行追加する。「ブランチ」列には検証対象のブランチ名を
  そのまま書く(slug は別のブランチと同じになりうるので、衝突の判定にこの列を使う。SKILL.md の `<feature>`)
- シナリオは `scenarios/<feature>/` に置き、ファイル名は必ず `<名前>.spec.ts` にする(それ以外は playwright に収集されず、`npx playwright test --list` でもエラーにならないまま静かにスキップされる)

## 共通化

保存場所のスイートは複数の機能で共有されるので、書く前に既存の `support/`・`seed/`・他機能の
シナリオを読み、共通化できる部分を積極的に切り出す。

- **切り出す条件**: これから書くシナリオ・seed のコードが、既存のコード(または同じバッチで書く
  別のシナリオ)と同じ処理を 2 か所目で必要としたとき。画面への遷移手順・フォーム入力・
  データ作成の手順などが対象。1 回しか使われないものを「将来使いそう」で先に切り出さない
- **切り出し先**: `support/` の素の TS モジュール(関数)か、Playwright の fixture(`test.extend`)。
  skill 独自の形式は持ち込まない。seed の手順は、全機能が前提にするデータ(どの機能でも要るログイン用
  ユーザーなど)なら `seed/common.ts` に寄せる。一部の機能だけが要るなら `support/` の関数にして各機能の
  seed から呼び、識別子は引数で機能ごとに分ける(機能間でデータを共有すると、片方の cleanup が
  もう片方の前提を消す)
- **既存コードも書き換える**: 切り出したら、同じ処理をしていた既存のシナリオ・seed もそのモジュールを
  使うように書き換える。書き換えは references/storage.md の「ロック」を取ってから行う。書き換える前に、書き換えるファイルを scratch など保存場所の外へ退避しておく
  (保存場所がリポの外や未追跡だと git で戻せないため)
- **書き換えたら確かめる**: 書き換えた既存の機能を `VERIFY_FEATURE=<その機能>` で実行し、
  書き換え前と pass/fail が変わらないことを確かめる(書き換え前の結果は、書き換える前に同じ worktree・
  同じ形で実行して控える)。今のブランチにその機能が入っていないなどで書き換え前から fail するシナリオがあっても、
  見るのは前後で pass/fail が一致することだけ。ただし globalSetup(seed)や auth-setup で落ちて、
  書き換えたコードが前後とも一度も実行されなかったなら「一致」ではなく「確かめられなかった」と報告する。平置きの旧シナリオは `VERIFY_FEATURE` で絞れないので全体実行で比べる。
  変わったら書き換えを戻し、報告に書く。書き換えたファイルは報告に列挙する
- **戻す前に照合する**: 書き換えた直後に各ファイルの `shasum` を控え、戻す前に一致を確かめる。
  一致しないファイルは、ロックを持たない追記(references/storage.md の「既存スイートへの追加で書く範囲」)が
  入っている。書き戻すとその追記が消えるので、戻さずに止めて報告する

## 探索(セレクタ・導線の確定)

spec を書く前に実画面を観察してセレクタと導線を確定する。手段は環境にあるものを使う:

1. `playwright-cli` が利用可能なら最優先(a11y スナップショットの ref 駆動で
   画面構造を確認できる)。**必須依存ではない** — なければ 2 へ
2. `npx playwright test --headed --debug` で実画面を見ながら書く、
   または一度実行して trace(`npx playwright show-trace`)から確定する

## 安定化

1. 観点単体で実行: `VERIFY_FEATURE=<feature> npx playwright test scenarios/<feature>/<ファイル>.spec.ts`
2. fail したら切り分ける(references/troubleshooting.md の「fail の切り分け」)
3. 全観点そろったら機能全体を実行: `VERIFY_FEATURE=<feature> npx playwright test`
