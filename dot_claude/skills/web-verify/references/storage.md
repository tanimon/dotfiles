# storage — 保存場所の解決・ロック・分類

保存場所を決める順序(明示指定 → 個人設定 → 質問 → 止める)は SKILL.md の「保存場所の決め方」。
決まった保存場所には、この順で **解決 → ロック → 分類** を行う。

## 解決

個人設定の書式(skill はこのファイルを読むだけで、作成も書き換えもしない):

```json
{ "default": "~/verify/{repo}" }
```

次の解決規則は、明示指定・個人設定・自由入力のどれで得たパスにも適用する。

- 相対パスは対象 worktree のルート(`git rev-parse --show-toplevel`)基準で解決する。
  `.claude/verify` なら worktree ごと(= ブランチごと)のコピーになり、git がブランチを分ける
- `{repo}` は main worktree のディレクトリ名に置き換える。worktree のディレクトリ名は乱数のことがあるので使わない。
  `git rev-parse --path-format=absolute --git-common-dir` の結果の末尾が `/.git` ならその親ディレクトリ名、
  そうでなければ(bare リポジトリ)そのディレクトリ名から末尾の `.git` を除いたもの。
  org が違う同名のリポは同じ `{repo}` になるので、そういうリポがあるならユーザーが設定のパスで分ける
- `~` はホームディレクトリに展開する

## ロック

保存場所は、別の worktree の web-verify と共有されることがある(`{repo}` 単位の保存場所など)。
多数のファイルを一度に書く **構造を作る作業** — scaffold・旧レイアウトの更新・別の保存場所への移管・
共通化による既存ファイルの書き換え — は、ロックを持っている間だけ行う。

ロックは 2 回取る。

1. **起動時**: 取って分類し、すぐ解放する。保存場所へ書けることの確認と、別のセッションが作業中かの確認を兼ねる
2. **構造を作る作業の直前**: 取り直して分類し直し、作業が終わるまで持つ。承認ゲートなど人の返答を待つ間は持たない。
   分類が起動時と変わっていたら(別のセッションが先に scaffold した等)、書かずに解放して止め、報告する

取得はディレクトリの作成で行う(`mkdir` は既にあれば失敗するので、取得と確認が 1 回で済む)。
`owner` の git 情報は対象 worktree から取る(保存場所が別の git リポジトリの中にあると、カレントディレクトリでは
そちらのブランチが記録される):

```sh
DIR="<保存場所の絶対パス>"
REPO="<対象 worktree の絶対パス>"
mkdir -p "${DIR}" && mkdir "${DIR}/.web-verify-lock"
printf 'branch: %s\nworktree: %s\nstarted: %s\n' "$(git -C "${REPO}" branch --show-current)" "${REPO}" "$(date -u +%Y-%m-%dT%H:%M:%SZ)" >"${DIR}/.web-verify-lock/owner"
```

- **`File exists` で取れなければ**、別のセッションが作業中か、中断したセッションの残骸。`owner` の中身を
  報告に載せて止める。消すかどうかはユーザーが決めるので、ユーザーが `! rm -rf "<保存場所>/.web-verify-lock"` で
  消せることを添える。期限切れとみなして自分で消すことはしない(生きているセッションのロックを奪いうる)
- **`Operation not permitted` で作れなければ**、保存場所がサンドボックスの書き込み許可の外にある
  (リポの外の保存場所では多い)。止めて報告する。`dangerouslyDisableSandbox` での再試行や許可の追加は、
  ユーザーがその場で明示的に求めたときだけ行う(許可を広げるかはユーザーが決める)。同じ場所への実行
  (`test-results/` などの生成)も同じ許可で書けるので、書き込みの確認は起動時の 1 回でよい
- **解放**は次のコマンドで行う。scaffold・旧レイアウトの更新・移管では完了マーカーを置いてから、共通化では
  書き換え後の再実行で一致を確かめてから解放する。途中で止めるときも、完了マーカーを置かずに解放してから報告する。
  解放が拒否されたら(リポの `.claude/` 配下など)、ユーザーに `! rm -rf "<保存場所>/.web-verify-lock"` を案内する

  ```sh
  rm -f "${DIR}/.web-verify-lock/owner" && rmdir "${DIR}/.web-verify-lock"
  ```

ロックが防ぐのは、ロックを取る web-verify 同士の衝突だけ。手作業のコピーなどロックを見ない書き込みで
作りかけの状態が残っても、完了マーカーが無ければ「スイートあり」とは分類しない。

## 完了マーカー

`<保存場所>/.web-verify-suite` は、構造を作る作業が最後まで済んだことを示す空ファイル。scaffold
(references/scaffold.md の「5. 生成の検証」の後)・旧レイアウトの更新・移管の最後に `touch` で置く。
スイートの一部として残し、保存場所がリポの中なら commit の対象にする。

## 分類

ロックを取った状態で、保存場所を次のどれかに分類する:

- **スイートがある** → 既存スイートへの追加
  - 新レイアウト: `playwright.config.ts`・`profile.md`・`support/run.ts`・`.web-verify-suite` がそろっている
  - 旧レイアウト: `playwright.config.ts` と `profile.md` があり、`support/run.ts` が無い(完了マーカーより前に
    作られたものなのでマーカーは見ない)。references/scaffold.md の「旧レイアウトの更新」を先に行う
- **空、または存在しない** → 新規 scaffold。`.DS_Store`・`.web-verify-lock`・`.env`・`.env.example` だけがある場所も空とみなす。
  `.env` は SKILL.md の「起動前に人間が確かめる事項」でユーザーが scaffold 前に置くことがあり、
  scaffold は `.env` に触れない(`.env.example` はテンプレートのコピーで置き換わる)。
  保存場所が対象リポの `.claude/verify/` ではなく、その `.claude/verify/` に `playwright.config.ts` と `profile.md` が
  あるときは、報告に「`.claude/verify/` に既存のスイートがある。移管は `/web-verify` の引数で指示すれば行う」と 1 行書く
- **それ以外** → 上書きせずに止める。空とみなすファイル以外があるのに上のどれにも当たらない場合で、
  ファイル名が scaffold と衝突しなくても止める。`support/run.ts` があって `.web-verify-suite` が無いもの
  (scaffold・更新・移管の途中で止まった、または別の書き込みが混ざった)もここに入る。対話中なら、別の場所
  (そのサブディレクトリ・別の空ディレクトリ・`.claude/verify/`)を `AskUserQuestion` で提案してよい。
  ユーザーが明示した場所でも同じ。質問できなければ blocked として報告する

## 既存スイートへの追加で書く範囲

ロックを持たずに書くのは次の 2 種類で、どちらも別の機能の追加と同時に走っても互いを上書きしない:

- 今回の機能のパスの新規作成: `scenarios/<feature>/`・`seed/features/<feature>.ts`
- 共有ファイル(`support/`・`seed/common.ts`・README.md・profile.md)への追記。読んでから書くまでの間に
  別のセッションが書き換えていれば Edit が失敗するので、読み直して追記し直す

既存の内容を書き換える変更(共通化での他機能のシナリオ・seed の書き換え、共有ファイルの置き換えなど)は
構造を作る作業として、ロックを取ってから行う。
