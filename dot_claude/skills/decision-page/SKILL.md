# decision-page

判断ページは、チャットを読んでいない人がページだけを見て判断し、回答を貼り戻せる 1 枚の HTML。部品は `assets/` にある: テンプレート `template.html`、貼り戻すテキストを組み立てる `serialize.js`、データからページを組み立てる `build.mjs`、データの見本 `example.json`(図つきの 3 問)。

## 1. 聞くか、どこで聞くかを決める

- 推奨が 1 つに絞れて、やり直せる判断なら聞かない。進めてから、結果と選ばなかった案を報告する。
- 次のどれかに当たれば判断ページを作る。
  - 図が無いと選択肢の違いが伝わらない
  - 問いか選択肢が 5 つ以上ある
  - 判断の根拠が AskUserQuestion の説明欄とプレビュー欄に収まらない
  - ユーザーがその場で答えられない(後で、または別の端末で答える)
- どれにも当たらなければ AskUserQuestion で聞く。1 問 2 択で、根拠が短い表に収まる判断は AskUserQuestion で足りる。

## 2. 中身を書く

問いと選択肢の中身は、pstack の ketchup skill(`~/.claude/plugins/cache/cursor-plugins/pstack/*/skills/ketchup/SKILL.md`)の「Write the reply」節にある action item の書き方に従う。根拠・リスク・推奨を書き、知らない事実は unknown と書く。判断ページで足すのは次のとおり。

- `context` は 2〜3 文で、何を決めるのか、なぜ今決めるのか、判断の前提を書く。
- 読み手はチャットを読んでいない人として書く。題・選択肢・図を含むページのすべての文で、略語・ツール名・リポジトリ内の用語(例: AFK、nono、heartbeat)は、意味の分かる言葉に置き換えるか、その場で説明する。
- 選択肢は 1 問に 2〜4 個。各選択肢に `gain`(得るもの)と `cost`(代償)を 1 行ずつ書く。推奨は 1 問に 1 つまで(`build.mjs` が検査する)。「その他(自由記述)」の選択肢と補足欄はテンプレートが足す。
- ページに載せる事実は、実測したものか、「推定」「未検証」と明記したものだけにする。根拠が表になるときは、`evidence` に HTML の表を置く(悪い値は `<td class="bad">`)。
- 問いの `id` は Q1, Q2…、選択肢の `id` は A, B… にする。ページの `id` は `<issue 番号か話題>-<短い英語>` にし、同じセッションの別のページと重ならないようにする。

## 3. 図を描くか決める

図は、選択肢の違いが構造(経路・依存・順序)の違いで、文章では追いにくいときだけ描く。描くときは次のとおり。

- インライン SVG で書く。Mermaid はローカルの HTML では描画されない。show-me skill の図の選び方は参考にしてよいが、`open` で開く手順はサンドボックスで塞がれるので使わない。
- 図と選択肢の文は同じことを言うようにする。選択肢の `gain` や `cost` が頼っているもの(例: 端末の出力)が図に無いときは、図に描くか `diagramCaption` で断る。図の各経路は、その案のラベルから読み取れるものにする。
- 箱は 8 個まで、`viewBox` の幅は 440 以下、文字の大きさは 15 にする。この大きさなら、幅 390px に縮んでも読める。
- 色はテンプレートのクラスで付け、SVG には色を直接書かない。テーマの切り替えはクラスが引き受ける。
  - 箱: `<g class="d-box">` の中の `rect` と `text`
  - 矢印: `<g class="d-edge">` の中の `path`。矢頭は `<marker id="arr">` の中の `class="d-head"` の `path`
  - 補助の文字: `text.d-sub`
  - 「見に行って気づく」と「向こうから届く」の区別: `rect.d-pull` と `rect.d-push`
- 選んだ案によって経路が変わる図は、要素に `data-when="Q1:A Q1:B"` を付ける。テンプレートは、選ばれた案(未選択のあいだは推奨案)に一致する要素だけを表示する。このことを `diagramCaption` に書く。
- 見本は `example.json` の `diagram`。

## 4. 組み立てて渡す

1. データを `~/.cache/decision-page/<id>.json` に書き、`node <この skill のディレクトリ>/assets/build.mjs ~/.cache/decision-page/<id>.json ~/.cache/decision-page/` を実行する。scratchpad は数日で消えるので、後で開かれうるページはそこに置かない。`<id>.html`(Artifact 用)と `<id>.local.html`(ローカル用)ができる。
2. 既定では `<id>.html` を Artifact ツールで公開し(icon は `decision`)、URL を渡す。
3. 次のどちらかのときは公開しない。`ls` で `<id>.local.html` があることを確かめてから絶対パスを示し、ユーザーに `! open <path>` を打ってもらう(サンドボックスの中の `open` は塞がれている)。
   - 内容を claude.ai に置きたくない(仕事のリポジトリ、機密)
   - Artifact ツールが無い
4. 「回答をコピーして、このセッションに貼り付けてください」と伝えて、ターンを終える。

## 5. 貼り戻しを読む

貼り戻しの形を決めているのは `serialize.js`。

```text
判断結果 <ページ id>「<題>」(<出典>)
Q1 <問いのラベル> → B「<選んだ案>」 (推奨は A「<推奨案>」)
Q2 <問いのラベル> → その他(自由記述) (推奨は C「<推奨案>」)
  記述: <自由記述。2 行目以降は字下げする>
Q3 <問いのラベル> → A「<選んだ案>」 (推奨どおり)
Q4 <問いのラベル> → 未回答 (推奨は A「<推奨案>」)
回答 3/4 問
```

- 1 行目のページ id で、どのページへの回答かを決める。
- 回答は、選んだ案のラベルで読む。記号とラベルが手元のデータと食い違うとき(ページを公開し直した後など)は、ラベルを正としてユーザーに確かめる。
- `Q` で始まる行の数が「回答 n/m 問」の m と合わなければ、貼り付けが途中で切れている。欠けた問いを聞き直す。
- 「記述」や「補足」に別の問いへの答えが書かれていることがある(例: Q2 の記述に「Q3 は B で」)。その問いの欄が未回答でも、それを答えとして扱ってよいかをユーザーに確かめる。
- 推奨案の無い問いには `(推奨…)` が付かない。記述が空の「その他」は未回答として出る。
- 未回答の問いは、推奨で進めるか聞き直すかをユーザーに確かめる。
