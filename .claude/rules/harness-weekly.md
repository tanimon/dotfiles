# Weekly harness job

`dot_claude/scripts/executable_harness-weekly.sh` は自己改善ループの週次ジョブの入口(ADR 0012、#398)。launchd(`private_Library/LaunchAgents/local.dotfiles.harness-weekly.plist.tmpl`、土曜 10:00、`RunAtLoad` は false)が `WorkingDirectory` を `~/.claude/harness` にして `nono run --profile claude-seal -- /bin/bash ~/.claude/scripts/harness-weekly.sh`(`--allow-cwd` は付けない。`WorkingDirectory` は nono の内側から symlink に差し替えられ、付けると差し替え先に read+write が付与されるため。`~/.claude` は claude-seal が付与しているので無くても動く) を起動し、スクリプトは nono の内側で `claude -p …` を直接呼ぶ。工程は抽出(harness-reflect)と選別(harness-review)で、claude を 1 回ずつ起動する(分類器の起動は別で、フラグも違う。下の「Failure Pattern への分類と週の再発率」)。工程の claude に渡すフラグは `dot_config/zsh/sandbox.zsh` の wrapper と同じ(`--settings '{"sandbox":{"enabled":false}}'` と `--dangerously-skip-permissions`)に、`--max-budget-usd`(工程ごとに既定 5、`HARNESS_WEEKLY_BUDGET_USD` / `HARNESS_WEEKLY_REVIEW_BUDGET_USD`)・`--session-id`・`--output-format json` を足したもの。
- **nono は plist で掛ける**: launchd は zsh の wrapper を通らないので、nono は明示しないと掛からない。スクリプトの中で掛けないのは、スクリプトが `~/.claude` 配下にあって nono の内側から書き換えられるため。スクリプトで掛けると、書き換えられた内容が次の土曜に境界の外で無人実行される(`dot_config/nono/CLAUDE.md` の「境界の外で無人実行するもの」)。スクリプトは `INSIDE_NONO_SANDBOX` が無ければ実行を拒む(誤用を止めるためのもので境界ではない)。手動で回すときはターミナルから `launchctl kickstart gui/$(id -u)/local.dotfiles.harness-weekly` を使う。
- **実行中の run は起動時の内容で動かす**(#515): 入口スクリプトは処理全体を `main` に入れ、最後に `main "$@"` と `exit` を 1 つのグループ(`{ … }`)にして呼ぶ。bash はスクリプトを実行しながら読むので、包まない形では、抽出と選別の claude(`~/.claude` に書ける)が同じ inode に書き換えた内容がその run の残りの部分で動く。1 つのグループにするのは、最後の行が `main "$@"` だけだと main が戻った後に末尾への追記が実行され、`exit` を後ろの別の行に置くとその行を上書きで差し替えられるため(shfmt は `main "$@"; exit` を 2 行に割るので、1 行の形は保てない)。`test/harness-weekly.bats` が抽出の claude の実行中に、末尾への追記と、最後の行の直前・本体の途中に命令を入れた上書きを行い、書き足した命令が実行されないことを確かめる。書き換え方ごとの効き方の実測は `docs/solutions/developer-experience/harness-weekly-job-measurements.md`。`source` する健全性の lib と Integrity Snapshot の lib は claude の起動より前に読み込みと実行を終えるので、後から書き換えてもその run には効かない(仕組みからの判断で、実測はしていない)。入口スクリプト自身について塞いだのは実行中の run だけで、書き換えた内容は次の週の run が nono の内側で実行する(ADR 0012 で受容した形。境界の外では動かない)。入口スクリプトが呼ぶ別のスクリプト(Verdict の CLI・再発率のスクリプトなど)は呼ぶたびにディスクから読まれるので、この形では守られない。それらは Integrity Snapshot が claude の起動前に取ったハッシュと照合する(「claude の後に使うファイルの書き換えの検出」の項)。
- **成功の判定**は exit 0 かつ結果の `is_error == false`。予算切れや認証切れ(`Not logged in`)の run は `subtype: success` や exit 0 のままでも `is_error` が立つので、終了コードだけを見ない。工程やその前提の確認(pnpm・origin の照会・worktree の準備など)が失敗すればその場で exit 1 し、heartbeat は書かない。実測は `docs/solutions/developer-experience/harness-weekly-job-measurements.md`。
- **heartbeat を書く条件**: heartbeat を書くのは `finish_run` だけ(書き込みは健全性の lib の `harness_health_write_heartbeat`)。`finish_run` に届くのは、抽出が成功したか省かれ、かつ次のどれかのとき: queue が空で選別を省いた(記録だけの PR が要る週はその作成まで成功した)/ 当日のブランチが origin にあり PR も既にある / 選別と `publish_review` が成功した(結果ファイルが決めた形で、commit が 0 件かつ Dropped Change が無ければ PR 本文の有無に関わらず選別の PR は作らずに成功(記録だけの PR が要る週はその作成まで)、commit と本文があれば push と PR 作成まで。それ以外の失敗の条件は `publish_review` のコメント。判定の記録の URL への置き換え(CLI の `publish`)は失敗しても WARN だけで、残った印を `finish_run` が捕まえる)。届いても、判定の記録(`queue-archive.md`)に PR になっていない採用が残っていれば(前の run の採用が PR にならなかった。Verdict の CLI の `unpublished` をブランチで絞らずに読むので、ループ以外の手書きの印も当たる)、または記録を読めなければ、heartbeat を書かずに exit 1 する。その週の工程がすべて成功していても、手で PR を作って CLI の `publish` で URL を記録するか queue に戻すまで毎週失敗する(エラーメッセージに印ごとの `publish` のコマンドが出る)。`state.json` に入れないのは、trigger と reflect も `state.json` を書き換えるため(lost update)。
- **予算と件数**: 1 回で扱うセッション数はプロンプトで上限を置き(既定 10、`HARNESS_WEEKLY_MAX_SESSIONS`)、予算は歯止めにする。予算だけだと、溜まった分を捌けない週は毎回予算切れで失敗し、進んでいても heartbeat が書かれない。既定値の根拠: Bash を 1 回呼ぶだけの実行でも固定の文脈で約 $0.4 かかり、上限の 10 件を処理した抽出の工程は約 $1.2 で既定の予算 $5 に届かなかった。予算切れの run は exit 1・`subtype: error_max_budget_usd`・`is_error: true` で終わるので、失敗として扱われ heartbeat は書かれない。 `--max-budget-usd` は厳密な上限ではなく、ターンの区切りでしか確かめないので 1 ターン分の費用だけ超えうる歯止めとして読む。実測は `docs/solutions/developer-experience/harness-weekly-job-measurements.md`。
- **抽出の入力は失敗の検出器で選ぶ**(ADR 0011、#403): 抽出の前に `~/.claude/scripts/harness-select-pending.sh --run <抽出の session id>` を実行し、pending の各 transcript を `harness-detect-failures.sh` にかけ、失敗が 0 件のセッションを pending から外す。残りが無ければ抽出の claude を起動しない。手動の `/harness-reflect` も同じスクリプトを(`--run` なしで)使う。信号の定義は検出器のヘッダ、Evaluator として CI で守るパスは `scripts/guarded-paths.txt`。セッションごとの信号別の件数は `~/.claude/harness/detections.jsonl` に、前の記録より増えた分だけを epoch 付きで記録し(pending に残って次の週にまた選別されても数え直さない)、PR の本文には `detection_section` が前回の heartbeat より後(heartbeat が無ければ直近 7 日)の行を、手動の reflect が記録した分も含めて集計して載せる。節を組み立てられなければ WARN を出して節を省き、PR の公開は止めない。採用 0 件で PR を作らない週の件数は、このファイルにだけ残る。抽出の入力を選ぶのはこの検出器だけで、SessionEnd の 10 ターンの閾値は pending に積むかどうかの閾値として別に働く。
- **Failure Pattern への分類と週の再発率**(ADR 0011、#404): pending の選別(`harness-select-pending.sh`)の直後、抽出より前に毎週(harness-review の選別を省く週や当日の PR が既にある週も)`harness-classify-failures.sh` が期間内に検出した失敗を `harness-failure-patterns.json` の一覧か `unclassified` に分類し(claude をツール無し・session を保存しない形で 1 回起動する。分類器の session id も `weekly-sessions.txt` に記録する)、`harness-failure-rates.sh record` が週の記録を `~/.claude/harness/failure-pattern-rates/<日付>.json` に書く。期間は heartbeat ではなく、分類に成功した前の週の記録の終わりから。分類の失敗は WARN にとどめ、その週は `classification: failed` として記録し、推移では「記録なし」と書く。その週の失敗は次の週の期間に含めて分類し直す(次の週の記録は 2 週分の期間になる)。期間を決められない(前の週の記録が読めない)か記録を書けない週は、週の処理を済ませたうえで run を失敗にし heartbeat を書かない(記録が黙って途切れないように)。形式・期間・率の定義は両スクリプトのヘッダ。一覧への追加は人が別の PR で行う(Evaluator。`scripts/guarded-paths.txt`)。
- **週の記録の commit**: 記録は選別の claude ではなくこのスクリプトが commit する(`commit_rate_records`。oxfmt を通し、`GIT_CONFIG_GLOBAL` が無ければ `~/.config/git/claude-code.inc` で署名する)。リポジトリの置き場は `docs/harness/failure-pattern-rates/`(1 週 1 ファイル。記録を含む PR が 2 本開いてもコンフリクトしない)。採用のある PR には origin/main に無い週の分をまとめて足し、本文に直近 4 週の推移を載せる(純増は記録の commit を足す前に数える)。採用の無い週は持ち越し、origin/main に無い週が 4 件たまり、開いているループの PR が無ければ、記録だけの draft PR を作る(queue が空の週も、選別が何も commit しなかった週も)。選別の claude の commit が記録に触れたら PR を作らずに失敗する。ローカルの記録の書き換えは Integrity Snapshot(「claude の後に使うファイルの書き換えの検出」の項)が見つける。
- **Eval Case と 2 アーム評価**(ADR 0011、#405): 選別に、採用したルールごとの Eval Case の依頼(または免除の理由)を `~/.claude/harness/eval-requests-<日付>.json` に書かせ(形式は harness-review スキルの「Eval Case requests」節)、`publish_review` が `harness-eval-cases.sh` で評価して「ルールの効果」の節を本文に足す。1 ケース 1 plugin を `~/.claude/harness/evals/<id>/` に作り、ルールは SessionStart の `additionalContext` で with の側にだけ注入する。判定の基準・除外・上限はスクリプトのヘッダ。評価の工程の失敗は WARN にとどめ、本文に「測っていない」と書いて PR は作る。評価のスクリプトと plugin の雛形が書き換えられていれば、評価も PR の作成もせずに失敗する(Integrity Snapshot)。採用したのに依頼の無いものは本文に名前が出る。予算は `HARNESS_WEEKLY_EVAL_BUDGET_USD`(既定 5)。残存: プロンプト・grader・with の側に注入するルール本文は選別(改善する側)が書くので、自明な grader で Δ を作れるうえ、PR で commit したのとは別の(答えを指定する)文字列を注入して Δ を作ることもできる(注入したルールと commit したルールの一致は確かめていない)。ADR 0011 は Eval Case を Evaluator に置くが、ここで固定できるのは評価の条件と判定の基準までで、依頼の中身は人の PR レビューで見る(実体の `request.json`。本文には注入したルールの sha256 の先頭 12 桁が載る)。
- **Rule Ledger**(ADR 0011、#406): 採用したルールごとの記録で、Eval Case の目録を兼ねる(却下・handoff は記録しない)。形・id・伏せ字の正本は `harness-rule-ledger.sh` のヘッダ。ローカルの `~/.claude/harness/rule-ledger/<id>.json` に 1 採用 1 ファイルで作り、リポジトリの `docs/harness/rule-ledger/` へはこのスクリプトだけが commit する。PR 番号は PR を作るまで決まらないので、`publish_review` は PR を作ってから `record_and_publish_ledger` で記録を作り、origin/main に無い記録のうち、この PR とマージ済みの PR の記録(前の週や手動の `/harness-review` から持ち越した分を含む)を 2 つ目の commit にして push し直す。開いたままの別の PR の記録はその PR のマージ後に、マージせずに閉じた PR の記録は写さない(PR の状態は gh で引き、引けなければ写さずに持ち越す)。そこで失敗しても PR と heartbeat は止めず、記録はローカルに残って後の PR が足す。採用の無い週は持ち越し、記録だけの PR(週の再発率の記録が 4 週分たまった週)にも載せる。書き出しは identity leak guard(origin/main の `scripts/scan-sensitive-info.sh` とパターン。worktree のものは選別の commit で弱められうるので使わない。ローカルのパターンはリポジトリ本体のものを渡す)と仕事のリポジトリ名(`~/ghq/github.com/<仕事の org>/` のディレクトリ名)で検査し、当たった記録は title と免除の理由を固定の文言で伏せる。初めて写した形を `~/.claude/harness/rule-ledger/exported/` に残して次からはそれを写すので、仕事のリポジトリの一覧から名前が消えても伏せた記録を伏せずに出さない。一覧に名前が増えて当たるようになった記録はさらに伏せるので、2 本の開いたループの PR に同じ記録が入っている間はその 2 本で中身が違いうる(残存。開いた PR どうしに入るのは、マージ済みの PR から持ち越した記録だけ)。org かリポジトリの一覧を引けなければ何も写さない(検査の空振りを避ける)。リポジトリ名は部分一致なので、一般的な語の名前のリポジトリがあると無関係な見出しも伏せる(安全側の誤り)。名前を含まない仕事の文脈は捕まえられない。選別の claude の commit が置き場に触れたら PR を作らずに失敗する。ローカルの記録・分類の記録(`classifications.jsonl`。Failure Pattern を引く)・`harness-rule-ledger.sh` 自身・Verdict の CLI の書き換えは Integrity Snapshot が見つける。CI のガードは置き場を `+` の行(追加だけ許す)で持ち、ループの PR による既存の記録の変更・削除を落とす。書き込みは一時ファイルからの `ln` で既存を上書きしないので、移行・手動の review・週次ジョブが同時に走っても記録を失わない(lock は要らない)。ただし週次ジョブの run の最中に手動の review が記録を作ると、書き換えの検出に当たってその run は PR を作らずに失敗する(記録は次の run が載せる)。記録に渡す評価の結果は、この run の評価の工程が書いて成功したものだけ(評価の前に消し、評価の後に封印する。選別の claude が置いた結果は記録しない)。判定の記録(`queue-archive.md`)は Verdict の CLI(`harness-verdict.sh` の `entries`。書式の解釈の正本はそのヘッダ、ADR 0017)で読み、採用は `kind` と `pr_url` で選ぶ。`migrate` が移すのは Eval Case を入れる前(`EVAL_CASES_SINCE`)に作った PR の採用だけ。それ以後の採用で記録が欠けたもの(PR にならなかった run を手で publish した採用など)は、`record --via manual` で作る。
- **Eval Case を nono の内側で評価するときの制約**: `--allow-tools Bash` を付けた起動は認証情報のファイルを辿れずに全 run が error になり、同じ起動の Bash を許可しないケースも巻き込む。Bash のケースは「評価できなかった」になるので、依頼はツール無しで「実行するコマンドを答える」形に寄せる。nono の外で評価する経路は、nono の内側から書ける plugin のフックを境界の外で無人実行することになるので作っていない。nono の内側の plugin eval は `/Users` を読めず `~/.claude/harness/evals` の下のケースを読み込まないので、評価は `/private/tmp/claude-<uid>/harness-eval/` の写しで走らせる。実測は `docs/solutions/developer-experience/harness-weekly-job-measurements.md`。
- **claude の後に使うファイルの書き換えの検出(Integrity Snapshot、ADR 0019)**: 抽出と選別の claude は `~/.claude` に書けるので、claude の後に job が実行する・読み込む・commit するファイルは `dot_claude/scripts/lib/harness-integrity.bash` が claude の起動前にハッシュを取り、使う直前に比べる。対象は claude の後に使う実行物と、commit するか PR の本文や記録の材料として読むデータ(検出件数の記録を含む)。一覧・照合・メッセージ・残存リスクの正本はその lib のヘッダで、週次ジョブは一覧を持たない。claude の後に `~/.claude/scripts` のスクリプトを呼ぶときは必ず入口(`harness_integrity_run`)を通し、push と `gh pr create` の直前には関門(`harness_integrity_gate`)を置く。改ざん・削除・照合不能は予約コード 3 で返り、run は heartbeat を書かずに失敗する。PR を作る前に落ちたら PR を作らず、作った後(URL の置き換えと Rule Ledger の記録)に落ちたら PR は残す。選別の claude が失敗した run(`report_failed_review`)が照合に落ちたら、手で公開する手順の代わりに、そのまま公開しないよう案内する。EXIT trap の `report_stops` は、入口を使えない run(lib の読み込みかスナップショットの前に止まった)と照合に落ちた run では Verdict の CLI を呼ばず、ブランチの Issue の本文にそのことを書く。テストは `test/harness-integrity.bats`(lib を直接 source する。実行物の Source が `scripts/guarded-paths.txt` に載っていることもここで確かめる)と `test/harness-weekly.bats` の contrast pair。
- **自分のセッションの除外は 2 段**: `HARNESS_DISABLE=1` で SessionEnd trigger に積ませず、加えて起動前に `weekly-sessions.txt` へ記録した session id を pending から実行の前後に外す。後者は環境変数が nono や hook まで届かなかった場合と、SIGKILL で後片付けの trap が動かなかった前回の積み残しのため。
- **再実行の安全性**: `weekly.lock/`(中に PID)で同時実行を防ぎ、持ち主が死んだ lock は取り戻す。nono の内側では `ps` が拒否され、別の nono インスタンスや境界の外のプロセスへの `kill -0` は EPERM になる(どちらも nono 0.79.0 で実測。`docs/solutions/developer-experience/harness-weekly-job-measurements.md`)ので、EPERM は生存とみなす(死んだとみなすと並走する)。1 日より古い lock は持ち主の生死に関わらず取り戻す(PID の再利用で EPERM が返り続ける場合のため)。抽出はセッションごとに「queue へ追記 → pending から外す」を済ませてから次へ進むので、途中で止まっても失うのは高々 1 セッション分。pending の読み取り失敗と、外す行が無いときの扱いは `strip_job_sessions` のコメント。
- **lock が防ぐのは週次ジョブ同士だけ**: 対話セッションの `/harness-reflect` や `/harness-review` と同時に走ると、pending と queue の書き換えが競合しうる。それらが検出件数の記録や Rule Ledger の記録を書くと、Integrity Snapshot が書き換えとして見つけ、その run は PR を作らずに失敗する。土曜 10:00 の起動と手動の reflect が重なる場合に限るので受容している。
- **選別と draft PR**: queue に項目があれば `~/.claude/harness/review-worktree` に worktree を切り(ブランチ `harness/review-<日付>`)、harness-review スキルをプロンプトで一部だけ変えて実行させる。queue と判定の記録は手動の review と共有する。選別は Verdict を Verdict の CLI の `settle` で記録する。採用の印の値(`<ブランチ> run <選別の session id>`)は prompt に書かず、選別の claude にだけ環境変数 `HARNESS_REVIEW_RUN` で渡し、CLI がその値から付ける。週次ジョブは印の書式を持たず、PR の URL への置き換え・この run の採用の列挙・PR になっていない採用の確認を CLI の `publish`・`adopted`・`unpublished` に印の値を渡して行う(書式の正本は CLI のヘッダ)(ADR 0017。`claude -p` の Bash ツールが nono の内側でも親の環境変数を引き継ぐことは #492 で実測した)。push と `gh pr create --draft` はスクリプトが固定の引数で行う(headless ではフックの `ask` が拒否になる。#429)。`permission_denials` は WARN で残す。理由と失敗の扱いは `prepare_worktree` / `publish_review` のコメント。手動の手順も同じ prefix(`harness/review-<日付>-manual`)を使い、CI はこの prefix でループの PR を見分ける(`scripts/check-guarded-paths.sh`)。
- **選別の結果ファイル**: 選別には毎回 `~/.claude/harness/review-result-<日付>.json`(`{"dropped": [...], "deploy_only": [...]}`、要素は 1 行の文字列)を書かせ、Dropped Change と Deploy-only Fix(`GLOSSARY.md`)の判定は PR 本文の有無ではなくこのファイルで行う(採用 0 件の週の本文にも指標などが載りうるため。#450)。ファイルが無いか決めた形でなければ失敗。空や空白だけの要素は数えない。申告は queue と判定の記録の観測と突き合わせ、食い違えば失敗する(#463。判定と見分けられない場合は `check_review_claims` のコメント)。PR 本文の「落とした変更」「deploy-only の修正」の節は claude に書かせず、スクリプトがこのファイルから足す。Deploy-only Fix は、結果ファイルを読めた時点で(後の判定で失敗する run や、選別の claude が失敗した run でも)`~/.claude/harness/deploy-only.md` に日付の見出し付きで追記し(既にある行は足さない)、`- ` で始まる項目がある間は briefing が警告する。人が適用したらファイルを消す。本文と結果ファイルは成功した run が消し、失敗した run は調べられるように残す。
- **処理対象が無い工程は claude を起動しない**(pending が空なら抽出、queue が空なら選別): 起動するだけで固定の文脈分(約 $0.4)がかかるため。両方を省いた週も、`finish_run` の確認を通れば heartbeat は書く(分類する失敗があれば分類器だけは起動する)。heartbeat は「claude と認証の経路が動いた」ではなく「ジョブが健全に回った」の意味になる。
- **停止を GitHub Issue で知らせる**(ADR 0012 の Consequences、#402): EXIT trap の `report_stops` が、この run の失敗・前の週に成功しなかったこと・ループの PR の放置・PR にならないループのブランチを、`.github/actions/harness-issue-alert` と同じくタイトルで重複を避けて Issue にする(何をどの条件で知らせるかは `report_stops` のコメント、判定は `lib/harness-health.bash`)。走らないジョブは自分の停止を知らせられないので、走らなかった週を知らせるのは次に走った run で、launchd が起動しなくなったままなら briefing の表示だけになる。本文は公開リポジトリに載るので、ログの行やエラー文は貼らず、固定の文言・日時・session id・`~` で書いたパスと対処のコマンドだけにする(詳細はログを session id で引く)。ジョブが lib を読み込むので、lib は Guarded Path として一覧に載せてある。
- ログは `~/Library/Logs/harness-weekly.log`。run ごとに `harness-weekly: start <時刻> session=<id> pending=<件数>` と、EXIT trap から `harness-weekly: end <時刻> session=<id> exit=<終了コード> pending=<前>-><後>` を出す。処理件数を claude の結果の要約文に頼らず pending の行数の前後で残すのは、予算切れなど失敗の run の結果には要約文が無いため(SIGKILL された run は end の行を残さない)。heartbeat の判定(閾値・plist の有無・level)の正本は `dot_claude/scripts/lib/harness-health.bash` で、briefing と doctor はその level を表示するだけ(heartbeat のファイル名と中身も、スクリプトの中ではこの lib だけが持つ)。テストは `test/harness-weekly.bats`(nono / claude / uuidgen / gh / pnpm をスタブにする)。
