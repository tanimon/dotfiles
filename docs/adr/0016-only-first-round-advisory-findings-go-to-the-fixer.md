# 修正エージェントに渡す参考指摘は、最初のレビューラウンドで出たものに限る

[ADR 0014](0014-advisory-findings-go-to-the-fixer.md) で参考指摘(Advisory Finding)も修正エージェントに渡すようにしたところ、LLM のレビュアーが修正した箇所に新しい参考指摘を出し続け、ループが `maxReviewRounds` まで回るようになった。計測した 7 件の実行のうち 4 件が上限に達し、修正必須 0 件のラウンドが続いても参考指摘の件数は減らなかった(3→2→1→3、3→3→1→4)。収束した 2 件の出力トークンは 15k〜27k、上限に達した実行は 52k〜205k だった(#426)。そこで、参考指摘を修正エージェントに渡すのは、実行全体の最初のレビューラウンドで出たものだけにする。ラウンド 2 以降に出た参考指摘は、動作確認の失敗による再入後のパスも含めて修正に回さず、最終報告の「参考指摘」節に載せるだけにする。0014 の判断(参考指摘を `receiving-code-review` で評価させる)は変えず、渡す範囲だけを狭める。収束条件・`maxReviewRounds`・`maxVerifyRetries` の既定値は変えない。

## Considered Options

- **参考指摘を修正した直後のラウンドで新しく出た参考指摘は修正に回さない** — 却下。「直後」と「新しく」の判定が、merge が振る key に依存して曖昧になる。
- **参考指摘だけの修正ラウンドに、`maxReviewRounds` とは別の上限(1 回)を設ける** — 却下。修正必須が混ざる実行ではラウンド数がほとんど減らない。
- **再入したときに参考指摘の修正を止める** — 単独では却下。計測した 7 件はどれも再入しておらず、観測された問題には効かない。ただし、この ADR の「実行全体の最初のラウンド」という範囲指定で、再入時の増加も同時に塞いでいる。
- **各パスの最初のラウンドで出た参考指摘を修正に回す** — 却下。動作確認の修正で入ったコードの参考指摘も直せるが、再入のたびに参考指摘の修正ラウンドが 1 回増える。そのコードにも修正必須のレビューはかかる。

## Consequences

- 元の差分に対する指摘でも、レビュアーの揺れでラウンド 2 以降に初めて出たものは直されず、報告に載るだけになる。
- 報告の「参考指摘」節は、修正に回さなかったものと、修正に回した後に再出現したものを区別しない。区別は統計の行の「報告のみ」の件数だけで示す(書式は spec `2026-10-03-review-advisory-fix-design.md`)。
